# patrol

整理の第二の入口。既存の repo / ディレクトリを深く読み、敵対的に疑って、「考えた方が良いこと（整理すべき話題）」を掘り起こす。

spar と patrol は同じ「疑う」エンジンを共有し、**話題が手にあるか / これから掘るか**だけが差す。spar は既に頭に話題がある状態で、いきなり疑うから入る。patrol は話題がまだ無い状態で、既存の repo / ディレクトリを把握してから疑い、話題を掘り起こす。

内部は三段の一本道:

> **把握（読む） → 疑う（叩く） → 探す（話題化）**

**patrol は確定・実行はしない。** 疑って話題を並べるところまでが patrol の仕事で、どれを整理するか選ぶのは人間。作業化のコミット（issue 化・close・commit 等）は人間が選んだ後、下流に渡る。

## 1. 対象の決定

**既定は「1つの repo / ディレクトリを深く」。**

- 引数（パス、または `<owner>/<repo>`）があればそれを対象にする。
- 引数が無ければ、今いる repo / ディレクトリを対象候補に挙げ、一問だけ「ここを点検でよいか？」と確認する。

**config ファイルは作らない・要求しない**（organize は作業ファイルを作らない。空でも即使える）。

複数 repo / org 横断は**二次モード**（→ 5）。深く読まないと「疑う」が成立しないため、既定はあくまで1つを深く。

## 2. 把握（読む）

対象が何で、どんな状態かを**実際に読んで**像を作る。ランク付けではなく読解。

- **何か**: README・既存 doc（`docs/adr/` 含む）・主要ファイルから、目的・スコープ・構造を掴む
- **どんな状態か**: 活動量（最終更新・commit 頻度）、手元の in-flight（未 commit の変更、push していない branch、`git stash`、TODO / FIXME）
- **何が既に言語化されているか**: どの doc があり、何を書いているか（無いこと自体は負債ではない → 4 の弁別子）

調べ方の規律: 読解は read-only（Read / Grep / Glob / `git log` / `git status` / `gh` API）。外部検索に機密を流さない。

## 3. 疑う（叩く）

把握した像を敵対的に叩き、**綻び**を surface する。これは spar と同じエンジン。中立な状態報告ではなく、像が保たないところを突く。organize の核心に沿って、綻びは 2 系統に出る:

**言語化の綻び**:

- **コード ↔ doc の食い違い**: 実装が doc の主張と違う
- **書かれざる決定**: churn / revert が示す、言語化されないまま繰り返し揺れた判断（→ ADR）
- **スコープのズレ**: 実際の作業が BRIEF の宣言を超えている / 外れている
- **用語の揺れ**: commit / doc で同じ概念が別語で呼ばれている（→ CONTEXT）
- **説明できない存在**: 誰も理由を言えないファイル・依存・設定

**flow の綻び（放置を含む）**: 作業が issue → PR → merge の規律に乗ったまま止まっている / 規律を外れている状態。把握で読んだ活動量・in-flight を綻びに翻訳する:

- **放置 issue**: 長く滞留した open issue（`gh issue list` で滞留日数が取れる）。issue が立ったのに branch / PR が続かず止まっている
- **放置 PR**: 長く滞留した open PR（`gh pr list`）。PR が立ったのに merge されず止まっている
- **放置 branch / 未 push**: merge されず残った branch、push されていないローカル branch（`git branch`）
- **滞留した in-flight**: 長期間 commit されていない作業・`git stash`（`git status` / `git stash list`）
- **main 直 commit / issue 無き作業**: issue → branch → PR を経ていない履歴（`git log`）

放置は活動量でスケールする。動いていない若いリポの放置は綻びが小さく、自然に足切りされる（→ 弁別子）。read-only の把握だけでは「その放置 issue / PR を close すべきか（意図的に parked か）」までは断定できないので、断定せず「疑うべき話題」として置く。

判定は organize の核心から演繹する（場当たりなヒューリスティクスは使わない）:

> リポの「**複雑さ × 活動量**」に対して「**言語化の度合い ＋ GitHub flow の規律**」がどれだけ追いついていないか（負債）を測り、綻びの大きい順に並べる。

これは複数レンズのうちの一つ。深く読む前提なので、負債はメタデータだけでなく実体（コードと doc の矛盾・書かれざる決定）まで対象になる。

**弁別子（lazy 原則を守る最重要ルール）**:

- **「doc が無い」では叩かない。** doc 不在そのものは負債ではない（organize の doc は lazy 作成＝ signal が出るまで作らないのが正常）。
- **負債は活動量でスケールする。** 活動に対して言語化 / flow が負けているときだけ負債。commit 数個・放置気味の若いリポは、doc が無くてもギャップが小さく、自然に足切りされる。
- 言い換えると patrol が拾うのは「signal が repo の歴史で繰り返し surface しているのに、誰も doc を作っていない / flow に乗せていない」状態。「signal が出たら作る」原則の自然な拡張であり、督促チェッカーではない。

## 4. 探す（話題化）と下流への振り分け

- 疑って見えた綻び一つ一つを「**整理すべき話題**」に翻訳し、**揮発するリスト**として会話に出す（commit しない・ファイル化しない。organize の「作業ファイルを作らない」規律に沿う）。各話題に、綻びの種類と推奨下流を添える。
- **人間が1件選ぶ。** 何を整理するかの選択権は人間が握る。patrol は複数を一度に surface するが、深掘りは1件ずつ直列に回す。
- patrol は既にその場で疑っているので、選ばれた話題は下流へ:

| 話題の性質 | 下流 |
|---|---|
| 疑い済みで打ち手が見えている | そのまま出口（残す＝ `create-issue` / commit / close 等）へ |
| さらに深掘り・計画を鍛える必要がある | `spar`（同じ疑うエンジンで続きを詰める）→ 出口 |

patrol は下流を**提案**するが、出口へ直行するか spar で深掘りするかを選ぶのは人間。read-only の把握だけで断定できない論点（放置 PR を close すべきか等）は、断定せず「疑うべき話題」として置き、判断は人間 / 下流に委ねる。

## 5. 二次モード（複数 repo / org 横断）

複数を抱えて「どこから手を付けるか」を俯瞰したいときだけ使う。全対象を毎回精読するとコストで破綻するため、二段構えにする:

- **Pass 1（広く・浅く・安価）**: 各 repo をメタデータ級の signal（最終 push の古さ・活動量・open issue / PR の滞留・README の有無）で横断ランク付けする。`gh repo list <org>` で列挙。
- **Pass 2（狭く・深く）**: 上位数件だけ、§2〜4 の「把握 → 疑う → 探す」を回す。

二次モードでも出力は揮発リストで、人間が1件選び、深掘りは直列。ランク付けは「どこから疑うか」の優先度であって、結論ではない。

## 6. 締め

点検は直列に回す。1件を下流に渡して片付いたら、残りのリストに戻って次を選べるよう促す。どの話題を扱っても、最後に「次に何をするか」を一言で示して終える（伴走）。
