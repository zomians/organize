# ADR-0006: ソースレビューにスコープレビューを足し、issue 外の変更を機械で検出する

- ステータス: 採用
- 日付: 2026-11-20

## 文脈

implement のレビューは、テストレビュー（issue・仕様書・テスト diff を見る。ソースは見ない）と `/code-review low`（diff を見る。issue は見ない）に分担されている（ADR-0005）。要件の未実装・誤りは「仕様 → テスト（テストレビュー）→ ソース（green）」の鎖で担保され、仕様書との食い違いは手順1・3 で止まる。しかし **issue とソースを同時に見るレビュアーがいない**ため、「テストが無く、バグでもない issue 外の変更」（ついでの改名・既定値の変更・issue 外の doc 書き換え等）はどちらにも引っかからない。仕様書の更新漏れも、この issue 外の変更から生じる。merge 前の PR 目視（人間）に委ねる案は退けた（自動実行モードでは人が介在せず、目視は保証にならない）。

## 決定

- ソースレビュー（手順7）を、**スコープレビュー**と `/code-review low` の並走にする。findings は混ぜずに並べて提示する
- スコープレビューは独自の read-only サブエージェント（Sonnet・fork しない）。入力は issue 本文・関連する仕様書・branch 全体の diff。観点は「diff の各変更が issue の FR / 受け入れ基準のどれかに紐づくか」の 1 つだけで、紐づかない変更を issue の該当箇所の引用つきで挙げる。再レビューはしない
- ソフトゲートとする（ADR-0003）。自動実行モードでは findings を控えて create-pr で PR と一緒に提示する
- テスト計画が `N/A` でもスコープレビューは走らせる（`/code-review low` だけ飛ばす）
- 手順4（ソース）に「issue に無い変更をしない」を予防として添える

## 理由

- **観測されないことは不在の証拠にならない**: 検出手段がなければ issue 外の変更は起きても気づかれない。YAGNI で「起きてから足す」は、起きたことを知る手段がある場合にしか成立しない。
- **テストレビューにソースを渡さない**: テストがソースに引きずられず仕様の写しになるのは、ソースを見せないからである（ADR-0005）。テストレビューは拡張せず、別のレビュアーを足す。
- **ADR-0005「ソースレビューを自作しない」を一部上書きする**: 退けたのは「基準なしの汎用レビューの再発明」だった。スコープレビューは issue を基準に持ち、観点が 1 つなので、過剰反応と保守コストの懸念に当たらない。バグ探しは引き続き `/code-review` に任せる。
- **止めずにソフトゲートにする**: FR の下準備（共通関数の切り出し・型の追加）は issue に直接書かれず、偽陽性が構造的に出る。findings は「紐づかないように見える」という推定であり、ADR-0005 が止める「仕様が 2 つある」確定した矛盾とは性質が違う。
- **`N/A` でも走らせる**: `N/A` を飛ばす理由は `/code-review` が空振りするという道具の都合で、issue と diff を比べるスコープレビューには当てはまらない。`N/A` の変更はテストレビューも通らないため、飛ばすと issue との突き合わせが一度も行われない経路が残る。

3 条件の確認: 後戻り困難（全案件に配る開発手順）／文脈なしには驚く（ADR-0005 の「ソースレビューを自作しない」を読んだ者が独自サブエージェントを見ると驚く）／実トレードオフ（検出の網羅 vs 使用量・偽陽性、止める vs ソフトゲート）。
