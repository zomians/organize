# ADR-0005: 実装フェーズ skill `implement` を新設し、issue（仕様）起点の TDD とレビューをそこへ移す

- ステータス: 採用
- 日付: 2026-11-12

## 文脈

organize は issue と commit のあいだ（実装）を持つ skill が無く、TDD は create-pr 手順1 の事後チェックだけだった。結果、テストがソースの後追いになり「テスト＝仕様＝品質担保」の手応えが無かった。また create-pr の `/code-review medium` は、仕様という基準を持たず fan-out する汎用レビューのため、時間がかかる割に過剰反応が多かった。

## 決定

- 実装フェーズ skill `implement` を新設する。順序は テスト → red 確認 → テストレビュー → ソース → green 確認 → ソースレビュー → commit
- TDD を回すか否かは issue のテスト計画が決める（不要なら `N/A`＋理由）
- テストレビューは organize 独自の read-only サブエージェント（Sonnet・fork しない・入力は issue / 仕様書 / テスト diff のみ）。指摘は本体が直して red 再確認、再レビューはしない
- ソースレビューは `/code-review low`。ADR-0003 のソフトゲートを引き継ぎ、置き場所だけ create-pr から implement へ移す
- 仕様書が恒久的な正、issue は差分。食い違ったら止まって問う
- テストレビューを通ったテストは凍結する。変更が必要、または green に届かないときは止まって問う（自動実行でも止まる）
- red 確認結果は PR 本文の「テスト」節に残す

## 理由

- **テストレビューとソースレビューを分担する**: `/code-review` は仕様を判定基準として受け取れず、「テストが仕様の写しか」は構造的に見られない。テストレビューだけを独自サブエージェントで埋める。ソースレビューは `/code-review` の本来の仕事で、テストレビューと green を経た後は拾うべきものが「テストの外側」に絞られるため low で足りる見込み。ソースレビューまで自作すると保守と verifier の再発明を背負う。
- **テストレビューをソースの前に置く**: テスト＝仕様なので、誤読はソースを書く前に潰すのが最も安い。後で見つかるとテストとソースの両方が手戻りになる。観点を「issue とテストの対応」に固定することで汎用レビューの過剰反応も避ける。
- **テストを凍結する**: green にならないときテストを書き換えると、テストは実装の後追いに戻り、この ADR が解こうとした症状が再発する。凍結の破れは `git diff` で機械的に判別できる。
- **仕様の食い違いは止める**: issue と仕様書の衝突は助言的な findings ではなく「仕様が 2 つある」状態で、どちらを優先しても誤りを黙って通しうる。ADR-0003 の「findings で止めない」はここには当てはまらない。

3 条件の確認: 後戻り困難（全案件に配る開発手順）／文脈なしには驚く（ADR-0003 を読んだ者が create-pr からレビューが消えているのを見ると驚く）／実トレードオフ（テストレビューとソースレビューの分担、凍結の厳格さ vs 柔軟さ、使用量）。
